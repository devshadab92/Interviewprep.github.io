Microservices Interview Questions

Service communication, API gateways, message brokers, and resiliency patterns.

What Is Microservice

Microservices Architecture is a design approach that breaks down an application into a set of small, independent services, each responsible for a specific business function. These services communicate with each other via lightweight protocols such as HTTP/REST or message queues. Unlike monolithic applications, where all components are tightly coupled and deployed together, microservices allow each service to be developed, deployed, and scaled independently.

Benifits

This approach enables easier maintenance, quicker updates, and faster release cycles. Each microservice is typically small enough to be managed by a small team,

offering greater flexibility in terms of technology stacks and deployment strategies.

Monolithic & Microservices

Monolithic architecture builds an application as a single, unified unit, making it simple to start but harder to scale and update, while microservices break the application into small, independent services that communicate via APIs, offering greater flexibility, independent scaling, and tech diversity, but with higher initial complexity and management overhead, ideal for large, complex systems. Think of a monolith as one big building (easy to enter, hard to change one room), and microservices as many small, connected pods (harder to set up, but easy to expand or modify one pod without affecting others). 

Monolithic Architecture

  • Structure: Single, unified codebase and deployment unit.

  • Development: Simpler initial development, but complexity grows with the application.

  • Deployment: Deploy the entire application as one piece.

  • Scaling: Scale the whole application, even for a single feature's need.

  • Tech Stack: Often uses a single technology stack.

  • Best For: Small projects, MVPs, or when speed to market is key. 

Microservices Architecture

  • Structure: Collection of small, independent, loosely coupled services.

  • Development: More complex upfront planning, but easier to manage specific services.

  • Deployment: Each service deployed independently.

  • Scaling: Scale individual services as needed (independent scaling).

  • Tech Stack: Can use different languages/tools for different services (polyglot).

  • Best For: Large, complex, rapidly evolving applications needing high agility and scalability. 

Microservices communicate with each other

Microservices communicate using Synchronous (request/response) methods like HTTP/REST or gRPC for immediate needs, and Asynchronous (event-driven) methods via Message Brokers (RabbitMQ, Kafka) for loose coupling and background tasks, often involving APIs (REST/gRPC), Message Queues/Streams, and sometimes Service Meshes (Istio) for advanced features like discovery, security, and load balancing. The choice depends on whether an immediate response is needed, balancing simplicity with resilience and scalability. 

Synchronous Communication (Direct Request/Response)

  • HTTP/REST: Most common, using standard HTTP methods (GET, POST) to call APIs exposed by other services, ideal for simple request-response patterns but can be chatty and tightly coupled.

  • gRPC (Google Remote Procedure Call): High-performance RPC framework using Protocol Buffers and HTTP/2 for efficient, language-agnostic communication, often preferred for internal service calls. 

Asynchronous Communication (Event-Driven)

  • Message Queues (RabbitMQ, SQS): A service sends a message to a queue, and another service consumes it later, decoupling them and preventing blocking.

  • Event Streaming (Apache Kafka): Services publish events to streams (topics), and multiple services can subscribe and react, perfect for data pipelines and real-time analytics.

  • Publish/Subscribe (Pub/Sub): A variant where publishers send messages to topics, and multiple subscribers interested in that topic receive the message, enabling broad broadcasting. 

Advanced Communication & Management

  • Service Mesh (Istio, Linkerd): A dedicated infrastructure layer that handles service-to-service communication, providing automatic service discovery, load balancing, encryption (mTLS), and observability.

  • API Gateway: A single entry point for external requests, routing them to appropriate microservices and handling cross-cutting concerns like security and rate limiting.

How does micro-services communicate

Microservices communicate using synchronous (direct request/response via HTTP/REST, gRPC) or asynchronous (event-driven via message brokers like Kafka/RabbitMQ) methods, often combined, to exchange data and trigger actions, enabling loosely coupled, independent service operation through APIs or message queues. 

Synchronous Communication (Request/Response)

  • What it is: One service sends a request to another and waits for an immediate response before continuing.

  • How it works:

    • REST (HTTP/JSON): Services expose APIs (endpoints) and use HTTP methods (GET, POST) with JSON for data exchange; widely adopted and easy to use.

    • gRPC (Protobuf): High-performance, uses HTTP/2 and binary serialization (Protocol Buffers) for faster, smaller messages, good for low-latency needs.

  • Use Case: When an immediate result is needed to complete a business process (e.g., checking inventory before checkout). 

Asynchronous Communication (Event-Driven)

  • What it is: Services send messages or events without waiting for a response, promoting decoupling.

  • How it works:

    • Message Brokers: Services publish events (e.g., "Order Placed") to a broker (Kafka, RabbitMQ), and other interested services subscribe to and consume these messages later.

API Gateway.

An API Gateway is a server that acts as an entry point for all client requests in a microservices architecture. Instead of clients directly interacting with each microservice, the API Gateway handles all incoming requests and routes them to the appropriate microservice. It also provides additional functionalities like load balancing, authentication, rate limiting, and response aggregation. API Gateways are especially useful in microservices environments where there are many small, independently deployable services. They simplify the client-side logic, as clients only need to interact with the API Gateway, rather than managing multiple endpoints for each service.

Microservices Communication

Microservices communicate with each other using various methods depending on the use case and system requirements. The most common method is HTTP/REST, where microservices expose their functionality via RESTful APIs. This is a simple and widely used method, as it allows for easy integration using standard HTTP methods (GET, POST, PUT, DELETE). Another popular method is message queues, like RabbitMQ or Kafka, which are used for asynchronous communication. This is especially useful for decoupling services and improving scalability. gRPC, a high-performance, language-neutral, and platform-neutral remote procedure call (RPC) framework, is another option often used for synchronous communication between microservices. Each of these methods has its own strengths and is chosen based on factors like latency, performance, and the need for asynchronous processing.

Message Broker Failiure.

When a service sends a message to a queue while the receiving (consumer) service is down, the system remains resilient because the message queue acts as a temporary storage buffer. Instead of the request failing immediately, the messages are held by the broker until the consumer service is back online to process them. 

Key Behaviors

  • Message Persistence: If the queue is configured for durability (saving to disk), messages will survive even if the message broker itself restarts.

  • Asynchronous Processing: The sending service can continue its work without waiting for the receiver to respond, preventing a single service failure from crashing the entire system.

  • Automatic Recovery: Once the consumer service recovers, it automatically pulls the pending messages from the queue and begins processing them from where it left off.

  • Load Management: If there are multiple instances of the consumer service, the queue can redistribute the work to the healthy instances so the system keeps moving. 

Specific Broker Examples

The exact behavior can vary slightly depending on the tool you use:

  • RabbitMQ: It holds messages in its queue until a consumer connects and acknowledges them. If a consumer crashes while processing, RabbitMQ will "re-queue" that specific message for another consumer.

  • Apache Kafka: It keeps messages in an append-only log. When a consumer goes down, Kafka keeps track of its "offset" (its last read position). When the service returns, it resumes exactly from that bookmark. 

Potential Risks

  • Queue Overflow: If the consumer stays down for too long, the queue might run out of memory or disk space.

  • Data Staleness: By the time the service comes back up, some messages (like a limited-time offer) might be too old to be useful.

  • Dead Letter Queues (DLQ): If a message fails to process multiple times after the service recovers, it may be moved to a Dead Letter Queue for manual inspection

Kafka Vs MQ

Feature Apache Kafka Traditional MQ (RabbitMQ, IBM MQ)
Primary Paradigm Distributed Event Streaming Asynchronous Messaging & Task Queues
Data Lifecycle Log-persisted; retained after consumption Transient; deleted immediately after ACK
Scaling Strategy Horizontal (via topic partitioning) Vertical (or complex, non-native clustering)
Consumer Model Pull-based (smart consumer, dumb broker) Push-based (dumb consumer, smart broker)
