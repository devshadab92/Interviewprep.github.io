What Is Azure Service Bus

Azure service bus is fully managed message broker (Message Queue and pub/sub) which store the messages from one services and other services are listening to that topic.

For example a customer placed an order on portal and order service will pass message to the Service bus and other service will be listening to the service bus topic so that inventory service will check the and manage the quantity and payment service process the payment and shipping service place the order and give the confirmation.

It enables asynchronous messaging between application and services.

Can Azure Service Bus Message be empty

Messages carry a payload and metadata. The metadata is in the form of key-value pair properties and describes the payload, and gives handling instructions to Service Bus and applications. Occasionally, that metadata alone is sufficient to carry the information that the sender wants to communicate to receivers, and the payload remains empty.

Azure Storage Queues Vs Azure Service Bus

Choose Storage Queues if:

  • You need a simple (REST-based GET/PUT/PEEK interface) queue with no particular additional requirements (point-to-point communication).

  • You need an audit trail of all messages that pass through the queue.

  • You expect the queue to exceed 80 GB in size.

  • You want to track progress for processing a message inside of the queue.

Choose Service Bus Queues if:

  • You need duplicate detection.

  • You need an at-most-once delivery guarantee.

  • You need a FIFO/ordering guarantee (using sessions).

  • You need to group messages into transactions.

  • You want to receive messages without polling the queue.

  • You need to provide role-based access to the queues.

  • You need to handle messages larger than 64 KB but smaller than 256 KB.

  • Your queue size will not grow larger than 80 GB.

  • You need to have dead-lettering.

  • You would like to be able to publish and consume batches of messages.

  • You want to use a publish-subscribe messaging pattern (using topics and subscribtions).

Receive & Peek in Service Bus

  • Peek: This method enables you to view messages without locking or receiving them.

  • Receive: Can work in 2 modes:

    • PeekLock (receives the message but keeps it peek-locked until the receiver abandons the message. The maximum timeout is 5 minutes before message expiration) and

    • ReceiveAndDelete (deletes the message after it is received).

So this means you'll use the Peek when your goal is to look at the messages without actually consuming them (maybe you're building a "Queue browser", ... or your process needs to decided if it wants/can consume the message). And you'll use Receive when you're really planning to consume the message and do whatever you need to do with it.

Why we use Scheduled Messages in Service Bus

Message scheduling is helpful when you want to postpone non-critical yet essential workloads to a later point in time. Then consumers can pick them up after peak hours. Scheduled messages can be canceled before the enqueue time. To cancel a message, you need its sequence number.

For example, you can delay email-sending tasks until midnight to save the computational capacity of consumers.

Another case is a consumer writing to an eventually consistent database. Adding a delay will help the message processor catch up with database writes made by upstream components.

Azure AD

Microsoft Entra ID (formerly Azure Active Directory/Azure AD) is a cloud-based identity and access management (IAM) service that provides centralized authentication, authorization, and security for applications and resources, including Office 365, Azure, and SaaS tools. It enables secure, single sign-on (SSO) and multifactor authentication (MFA) for internal employees and external users (partners/customers)

  1. Install NuGet packages: In your project, install the Microsoft.Identity.Web and Microsoft.Identity.Web.UI packages via the NuGet Package Manager Console:

bash

dotnet add package Microsoft.Identity.Web

dotnet add package Microsoft.Identity.Web.UI

  1. Update appsettings.json: Add the following configuration section to your appsettings.json file, replacing the placeholders with the values you copied from the Azure portal:

json

"AzureAd": {

"Instance": "https://login.microsoftonline.com/",

"Domain": "<your-tenant-domain>.onmicrosoft.com",

"TenantId": "Enter_the_Tenant_Id_Here",

"ClientId": "Enter_the_Application_Id_Here",

"CallbackPath": "/signin-oidc"

},

  1. Configure Program.cs (for .NET 6+):

using Microsoft.AspNetCore.Authentication.OpenIdConnect;
using Microsoft.Identity.Web;
using Microsoft.Identity.Web.UI;

  1. Add authentication services to the WebApplicationBuilder:

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddAuthentication(OpenIdConnectDefaults.AuthenticationScheme)
.AddMicrosoftIdentityWebApp(builder.Configuration.GetSection("AzureAd"));
builder.Services.AddControllersWithViews(options =>
{
var policy = new AuthorizationPolicyBuilder()
.RequireAuthenticatedUser()
.Build();
options.Filters.Add(new AuthorizeFilter(policy));
});
builder.Services.AddRazorPages().AddMicrosoftIdentityUI();

  1. Add authentication and authorization middleware to the pipeline before MapControllers() or MapRazorPages():

csharp

var app = builder.Build();
// ... other middleware ...
app.UseAuthentication();
app.UseAuthorization();
// ... other middleware ...
app.MapControllers();
app.MapRazorPages(); // Needed for the default Identity UI
app.Run();

 

Step 3: Secure your application 

Add the [Authorize] attribute to the controllers or actions you want to protect. When a user tries to access a protected resource, they will be redirected to the Azure AD login page. 

csharp

[Authorize]

public class HomeController : Controller
{
// Actions here will require authentication
}

Trigger Azure Function

Common Azure Function trigger types include:

  • HTTP Trigger: Executes a function when an HTTP request is made to a specific endpoint. This is commonly used for building APIs and webhooks.

  • Timer Trigger: Runs the function on a predefined schedule (e.g., every night at 2 AM, every hour), useful for periodic and time-based tasks.

  • Blob Storage Trigger: Initiates a function when a new blob is created or updated within a specified container in Azure Blob Storage. This is ideal for image processing or data file handling when a new file is uploaded.

  • Queue Storage Trigger: Triggers the function when a new message is added to an Azure Queue Storage queue.

  • Event Hub Trigger: Responds to events from Azure Event Hubs, used in scenarios involving high-volume data streaming, such as IoT device messaging.

  • Event Grid Trigger: Fires the function in response to events from Azure Event Grid, which can be custom events or events from other Azure services like Blob Storage (e.g., a file is deleted).

  • Cosmos DB Trigger: Automatically executes a function when a new document is created, updated, or deleted in an Azure Cosmos DB database collection.

  • Service Bus Trigger: Triggers the function in response to messages in Azure Service Bus queues or topics.

  • Durable Functions Orchestration/Activity Triggers: Used within the Durable Functions framework to manage long-running, multi-step, and stateful workflows.

  • IoT Hub Trigger: Processes events and messages from Azure IoT Hub, enabling backend processing for connected devices

Azure Function

Azure Functions is a serverless concept of cloud-native design that allows a piece of code to be deployed and executed without needing server infrastructure, web server, or any configurations. In addition, azure functions can be written in multiple languages such as C#, Java, JavaScript, TypeScript, and Python.

  1. Azure functions are lightweight and serverless.

  2. Azure functions are easier to write and deploy.

  3. Azure functions are fast to execute because there is no large application, startup time, initialization, and other events fired before the code is executed.

  4. Azure functions' execution is triggered when an event is fired.

  5. Azure functions are compute-on-demand, and that is scalable. When the demand for the execution increases, more resources are allocated automatically to the service, and when requests fall, all extra resources and application instances drop off automatically.

  6. Azure functions support programming languages, including ding C#, F#, Java, JavaScript, TypeScript, and Python. You choose your choice of language.

  7. Azure functions do not need any infrastructure and have 0 maintenance.

  8. The azure function can be built, tested, and deployed in the Azure portal using a browser.

  9. Azure functions are easy to upgrade and don't affect other parts of the website.

  1. Azure functions are language independent. Azure functions is a piece of code that is written to do a specific tasks. Azure functions is platform and language agnostic. You can write an Azure functions in one of the popular programming languages including C#, Java, JavaScript, TypeScript, and Python. You can deploy and execute Azure functions on any platform that can run .NET Core. 

  2. Azure functions are scalable. Azure functions uses compute-on-demand, which is scalable by design. When demand of execution increases, more resources are allocated automatically to the service and when requests fall, all extra resources and application instances drop off automatically. 

  3. Azure functions are lightweight and serverless. An Azure functions app is designed to a specific task and hence it is lightweight by design. Azure functions are serverless and do not require any Web servers or virtual machines to deploy and run.

  4. Azure functions are platform agnostic and run in their own process and environment. You can deploy Azure functions in any kind of configurations including Linux, Windows, or containers but Azure functions are available and can be consumed from any applications as long as they have access to the function.

  5. Azure functions are easier to write and deploy. Because of the nature of the Azure functions, they are easy to code, test, debug, and deploy. You don’t need a large team of developers to do that. A single developer can do everything.

  6. Azure functions are fast to execute because there is no large application, startup time, initialization, and other events fired before the code is executed. 

  7. Azure functions’ execution is triggered when an event is fired. Azure functions setup provides dozens of triggers that can be configured when an azure functions is executed. 

  8. Azure function can be built, tested, and deployed in Azure portal using a browser.

  9. Azure functions are independent. Azure functions are easy to upgrade and doesn’t affect other parts of a website or other applications.

  10. Azure functions use industry standard and can communicate with other APIs, databases, and libraries. This makes Azure functions more accessible in cloud native applications. 

  11. Azure functions can be cost effective because if their nature of running on demand.

When to use Azure Functions?

 

Azure functions service is a lightweight and serverless compute service that has its own use. You can’t replace a large website with Azure functions.

 

Here are some of the use cases of Azure functions: 

  • Scheduled Tasks

  • Reminders and Notifications

  • Lightweight Web API

  • Sending background emails

  • Running background backup tasks

  • Doing backend calculations

Azure AD Types

Key Types of Azure AD (Entra ID) Licensing & Functionality

  • Free Edition: Included with subscriptions for Azure, Dynamics 365, and Intune. Provides basic features like user management, self-service password change, and single sign-on (SSO).

  • Microsoft 365 Apps Edition: Includes Free features plus advanced features like Enterprise Mobility + Security (EMS) and advanced group access management.

  • Premium P1: Adds hybrid users (syncing on-premise AD to Azure), advanced delegation, conditional access, and identity governance.

  • Premium P2: Includes all P1 features plus Identity Protection, Privileged Identity Management (PIM), and risk-based conditional access.

  • Azure AD B2B (Business-to-Business): Designed for guest access, allowing external users to use their own credentials to access corporate applications.

  • Azure AD B2C (Business-to-Consumer): A customer identity management solution that supports millions of users and social identity providers (Facebook, Google).

  • Azure AD Domain Services (AD DS): Provides managed domain services (domain join, LDAP, Kerberos) without needing to manage domain controllers. 

Azure AD Device Identities

  • Azure AD Registered: Devices (BYOD) registered for management, often used for SSO.

  • Azure AD Joined: Cloud-only devices managed directly by Azure AD.

  • Hybrid Azure AD Joined: Devices that are both joined to an on-premises Active Directory and registered with Azure AD. 

Other Components

  • Azure AD Connect: The tool used to synchronize on-premises Active Directory with Azure AD.

  • Azure AD Groups: Includes security groups and Microsoft 365 groups, which can have assigned or dynamic membership. 

Type of Services

  • Infrastructure as a Service (IaaS):

  • Platform as a Service (PaaS):

Azure Storage

Azure Storage provides highly available, secure, and scalable cloud storage via services including Blob (unstructured data), File (SMB/NFS shares), Queue (messaging), Table (NoSQL key-value), and Disk (VM storage). These, along with specialized solutions like Data Lake Storage Gen2, are accessed through storage accounts using tiers optimized for access frequency (Hot, Cool, Cold, Archive). 

Key Azure Storage Services

  • Azure Blob Storage: Object storage for massive amounts of unstructured data (images, videos, logs). It includes block blobs (general), append blobs (logging), and page blobs (VHDs).

  • Azure Files

:

Managed file shares for cloud or on-premises deployments, supporting SMB and NFS protocols

.

  • Azure Disk Storage: Block-level storage volumes (managed disks) for Azure virtual machines.

  • Azure Queue Storage: A messaging service for reliable, asynchronous communication between application components.

  • Azure Table Storage: A NoSQL key-attribute store for storing, fast, structured, non-relational data.

  • Azure Data Lake Storage Gen2: A specialized, hierarchical file system for big data analytics built on top of Blob storage. 

Azure Service Bus

  • What is a Service Bus Namespace?
    A namespace is a logical container for all your Service Bus components, such as queues and topics. It provides a scoping container and can hold multiple entities. [1, 2, 3, 4, 5]

  • Explain the difference between Queues and Topics.

    • Queues: Support a one-to-one communication pattern where a message is sent by a producer and received by exactly one consumer.

    • Topics: Support a one-to-many (publish/subscribe) pattern where a single message can be received by multiple subscribers based on filter rules. [1, 2, 3, 4, 5]

  • What is the primary protocol used by Azure Service Bus?
    The primary protocol is AMQP 1.0 (Advanced Message Queuing Protocol), which is an open-standard wire protocol for messaging. [1, 2]

Advanced Features & Best Practices

  • What are Message Sessions?
    Sessions enable ordered processing (FIFO) of related messages. They allow you to group messages and ensure they are processed in the exact sequence they were sent. [1, 2]

  • What is a Dead-Letter Queue (DLQ)?
    A DLQ is a sub-queue used to hold messages that cannot be delivered or processed successfully (e.g., due to expired time-to-live or maximum delivery attempts). [1, 2, 3, 4, 5]

  • How do you handle duplicate messages?
    Service Bus has a Duplicate Detection feature. When enabled, the service keeps a history of all messages sent to the queue or topic for a specific time window and automatically drops any message with a duplicate MessageId. [1, 2, 3, 4, 5]

  • Explain Peek-Lock vs. Receive-and-Delete modes.

    • Peek-Lock: The receiver locks the message, processes it, and then deletes it. If processing fails, the lock expires and the message becomes available again.

    • Receive-and-Delete: The message is marked as consumed and deleted immediately upon being handed off to the receiver, risking data loss if the receiver crashes. [1, 2, 3, 4, 5]

Comparisons & Limits

  • What is the difference between Service Bus Queues and Azure Storage Queues?

    • Service Bus Queues: Support advanced features like FIFO sessions, transactions, dead-lettering, and larger message sizes (up to 100MB in Premium).

    • Storage Queues: Simpler, limited to 64KB per message, but can store up to 500TB of data total. [1, 2, 3]
